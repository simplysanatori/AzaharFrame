# AzaharFrame: technical notes

Azahar for Frame is a fork of [CitraVR](https://github.com/amwatson/CitraVR) that runs on the Valve Steam Frame. CitraVR is the Meta Quest build of [Azahar](https://github.com/azahar-emu/azahar). This document is for the person who maintains the fork: what is changed in the emulator's files, how to merge new versions, how to build and package. How the port works is in [TECHNICAL.md](TECHNICAL.md).

## Merging new versions

The remotes are `azahar` (azahar-emu/azahar), `citravr` (amwatson/CitraVR) and `origin` (this repository).

**Where it stands.** The branch `steam-frame` last took Azahar 2127.0-alpha4 in the merge commit `c7873cd44` ("Merge Azahar 2127.0-alpha4 into the Steam Frame branch"). Its second parent is Azahar's `e3c916e41`, the commit the `2127.0-alpha4` tag points at. CitraVR master as of that merge is `f71bf657d`.

**The content-level merge base.** CitraVR carries Azahar's code, but under rewritten commit ids: its history was rebuilt, so `git merge-base citravr/master azahar/master` finds an old commit (`3a4ebb141`) and a plain merge of either side shows a large false difference. That is why the two are never merged the same way:

1. **A new Azahar release (tag).** Merge the tag. Azahar's history is intact in this repository, so the merge base is the previous tag and only real conflicts appear, in the files marked `// AzaharFrame` and in the CitraVR files above.

   ```sh
   git fetch azahar --tags
   git switch -c merge/azahar-<tag> steam-frame
   git merge <tag>
   git grep -n "// AzaharFrame" -- src      # every marker must survive
   git grep -n "vr_immersive_mode_factor"   # the CitraVR shader change must survive
   ```

2. **New CitraVR commits.** Do not merge `citravr/master`. List what CitraVR added since the last sync and take the commits that touch the CitraVR files above (or the files this fork uses), one at a time:

   ```sh
   git fetch citravr
   git log --oneline f71bf657d..citravr/master
   git cherry-pick <commit>        # or: git diff <commit>^ <commit> | git apply -3
   ```

   If CitraVR has itself moved to a newer Azahar, take Azahar from step 1 and only the VR commits from here. After a sync, update the two commit ids in this section.

After either merge, rebuild with `steam-frame/build.sh`, run a game, and check the markers and the immersive shader change as above.

## Building

All on the Frame, with the tools SteamOS has: a C++ compiler (clang or gcc), CMake 3.24 or newer, Ninja, Qt 6 and SDL2 development files, Python 3, and SteamVR installed for running it.

```sh
steam-frame/build.sh 1.2.0      # configures build/, builds, packages steam-frame/release/azaharframe-1.2.0-linux-arm64.tar.gz and SHA256SUMS
steam-frame/install.sh          # installs that tarball and adds the Steam entry
```

The build uses Ninja, Release, `ENABLE_FFMPEG=OFF`, `USE_AUDIOTRACK=OFF`, Vulkan on and OpenGL off, tests, the room server, the web service, Discord and scripting off. `ENABLE_FRAME_XR` is on by default on Linux aarch64. It runs at the lowest priority and waits while the headset is in use (`~/.cache/headset-in-use`, or a game running under Steam), because a build next to a VR session ruins the session. `ccache` is used when it is installed (`~/.cache/azaharframe/ccache`). `CF_EXTRA_CMAKE_FLAGS` adds CMake flags, for example `-DENABLE_TESTS=ON` to build the unit tests in `src/tests/frame_xr`.

`ENABLE_FRAME_XR` needs no flag: `CMakeLists.txt` turns it on for Linux aarch64 (with Vulkan and Qt on), and `src/frame_xr/CMakeLists.txt` takes the OpenXR headers from `third_party/openxr/include` in the tree.

That build links the Qt 6 and SDL2 SteamOS has. The release is the portable build, `steam-frame/build-portable.sh 1.2.0`, which carries its own Qt and carries SDL3 and sdl2-compat; see [AGENTS.md](../AGENTS.md#portable-build).

`steam-frame/release/make-release.sh [version [build-dir]]` packs an existing build without building or touching Steam. Tarballs and `SHA256SUMS` in `steam-frame/release/` are ignored by git.

The release tarball holds, at its top level and without a folder around them:

| File | What |
|---|---|
| `azahar` | the emulator, stripped |
| `azaharframe.sh` | the Steam shortcut's target |
| `install.sh`, `uninstall.sh` | install and remove (see below) |
| `VERSION`, `LICENSE.txt`, `THIRD_PARTY_NOTICES.md` | |
| `art/` | the library art (`portrait`, `wide`, `hero`, `logo`) and the icon in four sizes; the program itself reads `logo.png` and `icon.png` |
| `tools/` | the texture pack converter (see [Texture packs in ASTC](#texture-packs-in-astc)) (the controller models, the Steam library entry, the dock icon and Emerald 3DS's pack are made by the program itself: `azahar --frame-controller-models`, `--frame-steam-shortcut`, `--frame-steam-art`, `--frame-dock-icon`, `--frame-emerald-build`) |

Files are packed by name, so settings, saves, keys, logs and game files cannot end up in it.

## Install and uninstall

`install.sh [--dry-run] [tarball]` copies the program and the helper scripts to `~/Games/AzaharFrame/app`, adds or updates the library entry "Azahar for Frame" through Steam's debugging port (`azahar --frame-steam-shortcut`), sets its art and icon, writes the SteamVR dock icon files (`azahar --frame-dock-icon install`), and sets SteamVR's per-app settings for the entry. Without an argument it installs the folder it is in when that is an unpacked release, else the newest tarball in `steam-frame/release/`, else the build in `build/bin/Release`. It never asks a question and exits 0 when Steam cannot be reached, after installing the files. Running it again updates the same entry, and your games, saves, keys and settings in `~/.local/share/AzaharFrame` are never touched. It refuses to run while the emulator is running.

`--dry-run` (or `AZAHARFRAME_DRY_RUN=1`) prints every file it would copy and every Steam and SteamVR call (with the JavaScript for Steam), contacts nothing and changes nothing.

`uninstall.sh [--purge]` removes the library entry (when Steam is reachable), the dock icon files (`azaharframe.desktop`, the `azaharframe` and `azahar` PNGs in `~/.local/share/icons/hicolor`, the SteamVR app manifest and its line in SteamVR's `appconfig.json`) and the program folder. `--purge` also deletes `~/.local/share/AzaharFrame` and `~/.cache/azaharframe`. SteamVR's per-app settings are left alone.

**Trial install.** Both scripts can work in a scratch folder without touching Steam or SteamVR:

```sh
export HOME=/tmp/af/h XDG_DATA_HOME=/tmp/af/h/.local/share
export AZAHARFRAME_APP=/tmp/af/app AZAHARFRAME_HOME=/tmp/af/home AZAHARFRAME_SKIP_STEAM=1
steam-frame/install.sh TARBALL
steam-frame/uninstall.sh --purge
```

With `AZAHARFRAME_SKIP_STEAM=1` the dock icon steps are skipped too (installing needs the entry's appid). To try them alone, with `HOME` at a scratch folder and `AZAHARFRAME_VRSERVER_RUNNING=0`, run `azahar --frame-dock-icon install DEST --appid N` and `azahar --frame-dock-icon remove DEST`.

## Texture packs in ASTC

Azahar decodes a PNG texture on a worker thread when a surface first needs it: about 0.4 s for 2048×2048 and 1.6 s for 4096×4096 on the Frame, while the game shows the original. Upstream keeps the decoded RGBA8 copy for the rest of the session; here it is dropped after upload (see Memory below), but every redraw of a new surface decodes again, and a large pack cannot be preloaded (the Ocarina of Time 3D 4K pack is 18 GB decoded). A KTX file in ASTC needs no decoding: reading it is the whole job.

**Format.** ASTC 4x4 by default (8 bits a texel, a quarter of RGBA8), 6x6 or 8x6 as options; those three are the ASTC sizes Azahar maps (`ASTC4`, `ASTC6`, `ASTC8` = 8x6). KTX 1, because dds-ktx reads KTX 1 only. Adreno has ASTC LDR in hardware; Turnip reports `textureCompressionASTC_LDR`, which Azahar did not enable on the device, so I enable it (and `textureCompressionBC`) and count a compressed format as supported only when its feature is on and `vkGetPhysicalDeviceFormatProperties` gives it `SAMPLED_IMAGE`. Without it the format is logged once at start and those textures keep the original.

**Colour.** Azahar uploads a custom PNG as `R8G8B8A8_UNORM`, the stored bytes with no sRGB decoding. The converter therefore encodes with the linear LDR profile and writes `GL_COMPRESSED_RGBA_ASTC_*_KHR`, which becomes `ASTC_*_UNORM_BLOCK`: the GPU returns the same values the PNG held. (An sRGB encode would come out darker; dds-ktx would not read the sRGB KTX format anyway.) Alpha is kept as stored.

**Flip.** With `flip_png_files`, Azahar turns PNGs upside down after decoding, and only PNGs. The encoder flips the image before compressing, so the KTX shows the same way; `pack.json` is copied unchanged, since any PNG kept in the pack still needs the flag.

**Mips.** For a pack with `skip_mipmap` Azahar generated the chain on the GPU with linear blits, which a compressed image cannot take. The encoder makes the whole chain down to 1×1 the same way (each level the average of the 2×2 texels above it, in the stored 8-bit values) and compresses every level. In the emulator, `LoadDDS` now finds every level of a DDS or KTX itself, because `ddsktx_get_sub` sizes compressed levels in 4x4 blocks, which is wrong for ASTC 6x6 and 8x6. `UploadCustom` copies all the levels the image has in one command, and mipmaps are never generated for a material with a stored chain. When a file has fewer levels than the guest surface, the custom image gets only as many levels as the file (`Material::ImageLevels`), so no level is left unwritten; a single-level DDS in a pack that has one file per level (no `skip_mipmap`) keeps the old behaviour. This does not depend on `skip_mipmap`, which also no longer rejects DDS files.

**Texture filters.** With a texture filter on, `GetTextureSurface` makes every game texture at the resolution factor, and `Upload` runs the filter into a second, scaled image, the one sampled. Upstream (as of 2026-11) gives a replacement the same scale: its Vulkan surface makes that second image too (at the material's size) and samples it, but `UploadCustom` writes the first one only, so every replaced texture showed black or uninitialised memory; OpenGL filtered the pack texture again. Here `UploadCustomSurface` makes the replacement at scale 1, both backends' custom constructors force scale 1 with no second image, and `ScaleUp` leaves a custom surface alone (a scaled copy would be made at the guest size in the custom format, maybe compressed). A PNG's level 0 upload also generates the rest of the chain when the pack does not skip mipmaps; a level with its own file overwrites its generated level when it uploads. Test: `src/tests/video_core/custom_texture_filter.cpp` (the cache with a fake runtime whose scaled surfaces sample a second image).

**Memory.** After a KTX or DDS material is uploaded, and no other upload waits for it, its file data is freed and the material goes back to unloaded; the next surface that needs it reads the file again on a worker (a few milliseconds). PNGs are freed the same way and decoded again when needed (memguard: keeping them grew memory with every texture the game had shown, up to the whole pack decoded). A file mapped to more than one hash in `pack.json` is kept. After a preload, KTX and DDS copies are freed and PNGs kept. A frame also stops starting uploads past 96 MiB, so a burst of large textures is spread over a few frames.

**The converter.** `core/custom_tex/convert.cpp` (a port of the former `convert_texture_pack.py`; it runs in the app, on a thread of its own, from the VR menu's pack page and the Flat game list) walks the pack (folders and files in name order, symlinked folders followed once), encodes every PNG on a pool of worker threads (all CPUs but one, two while a game runs; largest first; each worker at nice 19 and idle I/O priority), links or copies every other file, and rewrites `.png` names in the `textures` map of `pack.json` to `.ktx` (comments in `pack.json` are dropped, indent 4, key order kept). A KTX is written as `.part` and renamed, and a PNG whose KTX is newer is skipped, so a stopped run carries on. A PNG the encoder cannot read, or one over 16384 pixels a side (`STBI_MAX_DIMENSIONS`; downloaded packs are not trusted with more), is copied as it is and counted in `Result::kept_as_png` and `oversized`. The new pack gets `.azaharframe-ktx.json` (format, quality, the original's path relative to it, texture count, `kept_as_png`), written last; the emulator ignores it. `Activate` repoints `load/textures/<TitleID>` when it is a symlink (my own setup: `textures/<TitleID>` links to `textures-4k/<TitleID>`), or renames a real folder to `<TitleID>-original` and puts a symlink in its place; `Restore` reads the marker and undoes either. Progress is a callback (done, total, permille by texels); `Converter::Stop()` cancels the textures in hand (`astcenc_compress_cancel`) from any thread. `af_texconv` (built with the tests, not shipped) runs the same code from a terminal with the old script's options, for comparing outputs and timing.

**The encoder.** `core/custom_tex/ktx_encode.cpp` (the former `af-ktxenc`, now a library) compresses with ARM's astcenc (a submodule, `externals/astcenc`, pinned to 5.7.1 and built with NEON on arm64, default floating-point invariance) and decodes PNGs with the stb_image that astcenc ships. One compression context per worker, single-threaded, at astcenc's `medium` effort by default. Python has no image library on SteamOS (no Pillow, ImageMagick or libvips), which is why the mip chain is made in C++.

Numbers for the Ocarina of Time 3D 4K pack (2308 PNGs, 4.5 GB, 4.53 billion texels in level 0): 6.03 GB as ASTC 4x4 with mips (from `--estimate`), about 2.7 GB as 6x6, 2.0 GB as 8x6. A 4096×4096 texture is 22.4 MB as ASTC 4x4 with its 13 levels (10.0 MB as 6x6), against 89 MB of GPU memory as RGBA8 with generated mips. Encoding one 4096×4096 texture on one Frame core, with a build running beside it at the same priority: 18 s at `medium`, 6.4 s at `fast`, 22 s for 6x6 at `medium`. For the whole pack that is about 82 CPU minutes at `medium` (about 15 to 20 minutes on seven cores) and 29 at `fast`. Decoded and compared with the flipped PNG, level 0 is 47.5 to 48 dB PSNR in colour at `medium` (fast 0.7 dB less, 6x6 about 40.5 dB), and the channel means match to 0.05, so nothing is lightened or darkened. Building astcenc and the encoder took 14 s with two jobs.

## Preload and the memory limit

Preload Custom Textures reads every file of the pack into memory before the game starts. The Frame shares its 15.3 GB with SteamVR, passthrough, the compositor and the GPU. Two starts of Ocarina of Time 3D with the 4K pack as ASTC (2308 files, 6.03 GB, about 5.6 GB of file data held in memory) froze the headset at 1957 of 2310: the old limit allowed all of RAM but 2 GB, the system thrashed in zram for over a minute (one display frame took 57 s), and a watchdog rebooted it. No process was killed.

- **The budget** (`video_core/custom_textures/preload_budget.h`, unit-tested in `src/tests/frame_xr/preload_budget.cpp`). The pack's cost is worked out before anything is read (`CustomTexManager::PreloadEstimate`): a DDS or KTX file as it is on disk, a PNG decoded (width x height x 4 from its header), each file once. It must fit, with 10 % to spare, in MemAvailable less a reserve of 4 GB (or a quarter of RAM, if more; `AZAHARFRAME_PRELOAD_RESERVE_MB`), and in what this process's cgroup still allows under its MemoryHigh or MemoryMax (page cache not counted) less 1.5 GB (or 20 % of the limit). Otherwise nothing is preloaded and the pack loads as needed, with the toast **Texture Pack Too Large to Preload** (the status bar in Flat). While it reads, the same room is read again every 8 materials or 64 MB; under a reserve it stops, drops what it read, loads as needed, and says **Preload Stopped: Low Memory**. Either toast is a long one (5 s), and the in-game menu's next open then offers **Optimize <Pack> for Frame?** on the active pack when it is PNG with no optimized copy (`FrameMods::NudgeOptimizeActive`, whatever its size); the Preload question does the same when its status row says **Too Large to Preload Right Now**. Each file's page cache is dropped once read (`POSIX_FADV_DONTNEED`), so the pack is not held twice.
- **After a preload** the CPU copy of a KTX or DDS material is freed once it is uploaded (the GPU copy is in the same RAM); a PNG keeps its decoded copy, which is what the preload saves.
- **The question.** Turning Preload on asks **Preload Textures?** with the pack's cost, the memory in use, Azahar's limit and whether the pack fits now, from the same functions (`Summarize`, `MakeConfirmText`): the VR menu's Textures segment (`MenuCommand::AskPreload`, `ModsDialogKind::Preload`) and Flat's Enhancements checkbox (`citra_qt/frame_preload_confirm.cpp`). Off by default.
- **The memory limit** (`azaharframe.sh`). The emulator runs in a user scope, `systemd-run --user --scope -p MemoryHigh -p MemoryMax -p MemorySwapMax`. MemoryMax is the smaller of 65 % of RAM (`AZAHARFRAME_MEMORY_MAX_PCT`, 30 to 90) and MemAvailable at launch less 2 GB for SteamVR and the compositor (`AZAHARFRAME_MEMORY_RESERVE_MB`), but at least 4 GB (`AZAHARFRAME_MEMORY_FLOOR_MB`: a game with its GPU memory is about 2.2 GB here, and writing a save state adds its serialized system, about 300 MB for a big game, for a moment); `AZAHARFRAME_MEMORY_MAX_MB` sets it outright. MemoryHigh is 1/12 less, with 2 GB of swap (`AZAHARFRAME_MEMORY_SWAP_MB`). GPU memory is charged to the scope too: msm's buffers are shmem, and the scope's `memory.stat` shmem matches `drm-total-memory` in the emulator's fdinfo. systemd-run executes the emulator itself, so its process, environment, folder, parent (Steam's reaper) and `oom_score_adj` stay as they were; only the cgroup changes. A trial scope runs first (about 10 ms); when systemd-run is missing or fails, the emulator runs as before. `launch.log` says which (`memory: ...`). `AZAHARFRAME_MEMORY_SCOPE=0` turns it off. A runaway emulator is then killed by the kernel (exit status 137) instead of freezing the headset. The scope is not collected, so its result can be read: on `oom-kill` the launcher writes the limit to `out-of-memory` in the data folder, and the next start shows **Azahar Ran Out of Memory** once (VR and Flat), naming the pack and Preload as the usual cause, in the crash report's dialog (below). When a game stops, the log has `memory after stop: RSS ... (heap, files, shared), GPU ..., group ..., available ...` (after `malloc_trim`) and the custom texture data still held.
- **A way out while a game starts** (`frame_xr/startup_escape.h`). Until the game's screens are live (preload, shader cache) the game's controls do not run. Menu or View held 3 s stops the game (Stopping... from 1.5 s); if the game still runs 10 s later, Azahar quits.
- **The warning before the limit** (`frame_xr/mem_watch.h` the rules and texts, `citra_qt/frame_memwarn.cpp` the thread and the Qt dialog, `GMainWindow::FrameMemoryEvent`). A thread reads the scope's `memory.current`, `memory.max`, `memory.high`, `memory.swap.current`, `memory.stat` (file, shmem) and `memory.events` (high) every 2 s, from `/proc/self/cgroup`; with no scope or `memory.max` "max" it does not start. Use = current less the page cache (file - shmem; GPU buffers are shmem and stay) plus swap. At 85 % of `memory.max` the toast (VR) or the status bar (Flat) says "Running Low on Memory: X of Y GB", again only under 80 % and back, at most every 2 min. At 93 %, or a `high` event while at 85 % (the page cache alone reaches MemoryHigh while a pack is read, so a `high` step under 85 % is ignored), the game pauses: the in-game menu's notice in VR (a third button, `ModsDialog::extra`, `NoticeAnswer` 2), a Qt dialog in Flat. Again only under 88 % (or 5 % under where a `high` step paused it) or 3 % higher. **Turn Off Custom Textures** (offered, and advised in the text, only when the pack's pixel data, `CustomTexManager::HeldBytesHint`, is at least 10 % of the limit and 128 MiB: `MemWatch::TexturesMatter`) sets `custom_textures` off for the running game (`Settings::values.custom_textures_off_for_memory` remembers the layer; `QtConfig::SaveUtilityValues` keeps writing it as on; `ShutdownGame` puts it back); the renderer's next `TickFrame` unregisters its surfaces and `CustomTexManager::Unload` drops every texture's pixel data and calls `malloc_trim`. While at 93 % (or paused for it and not yet re-armed) `FrameMemWarn::Critical` sets `Autosave::Gates::memory_low` and every autosave is skipped with "memory is almost full" in the log. No Save State in the dialog: a save state needs its serialized system more while it is written. A save or load in progress is a known, bounded spike: `common/transient_memory.h` counts the bytes it holds (the serialized system from `StateWriteBuf` until the writer lets it go, the decompressed state while it is read), the watch leaves them out of its rules (`Watcher::Step`'s `transient`; logged as "a save state holds N MiB for a moment: not counted"), ignores a `high` step taken while they were held, and samples every 250 ms while they are held, so the sample right after sees the memory without them and pauses then if that is still too much. Nothing gates a manual save near the limit (as before): the pause level leaves 7 % of the limit, less than a big game's state under a limit of about 4.4 GB, so a save started just under it can cross the limit; the slot keeps its old file (the write is atomic).
- **Save states and memory** (`core/savestate.cpp`, `core/autosave.cpp`, `video_core/rasterizer_cache/rasterizer_cache.h`). `System::SerializeState` writes the archive into one string reserved up front (`ReserveForState`: the last state's size + 32 MiB, at least all guest memory + 96 MiB; only address space until written), and `WriteStateFileFrom` compresses it straight into `<file>.tmp` (`Common::Compression::CompressDataZSTDTo`, `Common::AtomicFileWriter`), then renames it over the slot: about 1x the state in memory where the old ostringstream, `str()` copy and `CompressDataZSTD` buffer held about 3x (Kid Icarus: 306 MiB serialized, 919 MiB more at the peak before, 305 MiB now). The file is the same: the 256-byte header, then one zstd frame (level 3, 2 MiB window, the content size), so states load in older builds and upstream Azahar as before. A slot's save (Quick Save included) is serialized on the emulation thread and compressed and written by the autosave writer (`System::SaveStateInBackground`; one state in memory at a time: it waits for a write still running), so the game stands still for the serialization alone; a failed write is told by the writer's `on_done`, queued to the UI thread (`FrameAutosaveWritten`, `Autosave::SlotSaveFailure`, `FrameSlotSaveFailed`: Couldn't Save State with its reason; a toast in VR once the game has stopped), so it comes at once whether the game runs, is paused in the in-game menu or has stopped, and never through `RunLoop`, where it would be taken for a failed Load Anyway; a load waits for the writer first. Known and accepted: the UI reads a slot's header for Load Anyway and Undo Load's text before a write still running (about a second after a save) has replaced the file; the core loads the new file all the same, and the worst case is an unneeded Load Anyway question. A save killed during its write leaves `<slot>.cst.tmp`, removed at the game's next start (`RemoveStaleStateTemps`). `AZAHARFRAME_TEST_SAVE_FAIL="11,12"` (hooks builds) fails those slot writes, counted from 1. Loads read the decompressed state in place (`StateReadBuf`), not from an `istringstream` copy. Undo Load's file is still written on the emulation thread before the load, the same way. A disabled cube texture unit is bound with the null sampler (`NULL_SAMPLER_ID`); it used `GetSampler(NULL_SURFACE_CUBE_ID)`, sampler 1, which a cache made by a state load does not have yet, so a garbage handle went into `vkUpdateDescriptorSets` and Turnip crashed (Kid Icarus); `RasterizerCache::GetSampler` now gives the null sampler for an id that names none. `RasterizerCache::ClearAll` (every save state calls it) unregisters each surface into the deletion queue: it used to clear only the page table, leaving every surface with its GPU image alive until the game stopped, so memory grew by the game's working set with each save (test: `tests/video_core/rasterizer_cache_clear.cpp`).
- **Tests.** `steam-frame/test/launch-mode-test.sh` covers the scope. `src/tests/frame_xr/mem_watch.cpp` the warning's rules with fake cgroup files; `AZAHARFRAME_TEST_MEMWARN_BALLAST="SECONDS:MB,..."` holds that much more memory from that second of the watch on ("SECONDS:87%": enough to reach 87 % of the limit), `AZAHARFRAME_TEST_MEMWARN_ANSWER=textures|resume|stop:SECONDS` answers the dialog, `AZAHARFRAME_TEST_MEMWARN_SHOTS=DIR` saves the Qt dialog; `frame_xr_menu_dump` draws the toast and the VR dialog (`memwarn-*.png`). Mock runs: `AZAHARFRAME_PRELOAD_FORCE=1` skips the check before the preload (the check while it reads stays), `AZAHARFRAME_TEST_PRELOAD_DELAY_MS` waits after each material, `AZAHARFRAME_TEST_PRELOAD_SHOT=DIR:SECONDS` saves the Flat question; `frame_xr_menu_dump` draws the VR one with this machine's numbers (`AZAHARFRAME_DUMP_PRELOAD_BIG`, `_SMALL`: the packs' bytes). Run anything with a real large pack inside a capped scope (`systemd-run --user --scope -p MemoryMax=3G -p MemorySwapMax=0 ...`).

## Crash reports

- **The run marker** (`common/frame_crash.{h,cpp}`). At start `FrameCrashDialog::Detect` (`citra_qt/frame_crash_dialog.cpp`, right after the log starts) reads what the last run left in `user/crash-reports/`, then `Common::FrameCrash::Start` writes this run's `running` (pid, version, release, mode; the game, its title ID and its settings from `GMainWindow::BootGame`; a cause noted on the way) and installs handlers for SIGSEGV, SIGBUS, SIGILL, SIGFPE, SIGABRT and SIGTRAP and for `std::terminate`. A fatal signal writes `last-crash`: first with `write()` only (the signal, the address, the thread name, pc and lr, `/proc/self/maps`, then `fsync`), then the stack (`backtrace()` addresses and `backtrace_symbols_fd` lines). `backtrace()` is the one call that is not async-signal-safe (libgcc's unwinder can take a lock the crashed thread held; it is loaded at start so it never loads in the handler), so the handler first sets SIGALRM to its default action and calls `alarm(5)`: a handler that hangs ends the process 5 s later with what it wrote by then, and one that finishes cancels it. It then restores the handler that was there before and lets the signal take the process. dynarmic installs its fastmem SIGSEGV handler later and passes on what is not its own. A clean quit (`LaunchQtFrontend`, after `FrameXr::Shutdown`) removes both files; a marker whose pid is a running `azahar` belongs to another copy and is left alone.
- **Causes**: `NoteCause` from the four `vk::DeviceLostError` catches (`DeviceLost`), `GMainWindow::OnCoreError` (`ErrorCoreExceptionRaised`: `ArmException`; `ErrorUnknown`, which ERR:F sets: `CoreFatal`) and the startup escape's quit (`Stuck`). `Classify` (`core/frame_crash_report.cpp`): the launcher's `out-of-memory` (memguard; `FrameMode::TakeOutOfMemory`) first, then device lost, then a fatal game error, then a signal, else Closed Unexpectedly.
- **The report** (`CrashReport::Build`): the run's log is `azahar_log.old.txt` by then (the last 2,000 lines, the GPU and driver from its `VK_DEVICE:` and `VK_DRIVER:` lines), the stack starts at the faulting pc (the handler's frames go), each module a frame is in with its base, size and GNU build id read from the file, plus clues (the crash guard's new mods, Load Anyway's marker). `Scrubber` replaces the home folder, the host name and the user name (not SteamOS's own `steamos` or `deck`); `ScrubNetwork` replaces IPv4, IPv6 and MAC addresses in the log tail (not in what the player typed). `ReportText` is `report.txt`; `FullText` adds the log, and is what See What's Sent shows.
- **The dialog**: a Qt dialog in both modes (at start in VR no game runs, so there is no in-game menu; Azahar's window is the VR panel). In VR a tap on **What Were You Doing?** opens the game keyboard panel (`FrameXr::OpenGameKeyboard`, `frame_xr/menu/crash_note.h`: multi-line, 500 characters, Cancel, Clear and Done); with no game running `VrUi::SwkbdUnderWindow` puts it under Azahar's window, which stays in view without input, and Done puts the text in the box.
- **Send Report** (`core/frame_crash_send.cpp`): sentry-native 0.17.6 in `externals/sentry-native` (in the tree: no `external/`, tests or examples), built static with `SENTRY_BACKEND=none` and `SENTRY_TRANSPORT=none`. No backend because the app records the crash itself and Sentry may only start once the player taps Send (crashpad needs a handler program, breakpad and inproc a handler installed at start); no transport because it would need libcurl in the bundle, so a transport over the httplib and LibreSSL the mods already use posts the envelope. `sentry_init` for that one report (release `azaharframe@<version>`, or the commit for a development build; environment `production` with `AZAHARFRAME_RELEASE`, else `development`; no sessions, client reports, breadcrumbs or symbolication of this process's addresses), the event with the stack as an exception and `debug_meta` of the crashed run's modules (`BeforeSend` replaces Sentry's own and drops its OS context), `report.txt` and `azahar_log.txt` attached, then `sentry_close` and its database folder removed. The DSN is `-DAZAHARFRAME_SENTRY_DSN` (or the variable of that name at configure time) into the made `frame_crash_config.h`; `steam-frame/release/sentry-dsn.sh` takes it from the environment or `~/.config/azaharframe-dev/sentry-dsn`. Without one there is no Send Report.
- **Report a Problem**: `FrameCrashDialog::ShowReportProblem` (Help > Report a Problem... in Qt; the VR menu's Settings, General, Help rows `Id::ReportProblem` and `Id::AboutApp` send `MenuCommand::ReportProblem` / `About`, which open the dialogs in Azahar's window like More Settings). `CrashReport::BuildManual` is `Build` for this run (`azahar_log.txt`, the settings now) with `Kind::Manual`: no reason, no stack. The same dialog with **What Happened?** (Send Report greyed while it is empty), **Include a Screenshot** while a game runs (off by default; `g_frame_report_problem` in `citra_qt.cpp` asks the renderer for a screenshot at 1x through `RequestScreenshot`, the top and bottom screens of the layout and never the XR view; a paused game runs until that frame, as Tools > Capture Screenshot does; 3 s at most), and Cancel. `screenshot.png` is a third file. Sentry gets a `warning` event titled with the first line of the note (`ManualTitle`), tags `report: manual` (`crash` for crashes), the settings in `extra`, no exception. With the in-game menu showing Azahar's window, `VrUi::SwkbdUnderWindow` also puts the keyboard under the window. **About Azahar for Frame** (`ShowAbout`) shows the version, the build, GitHub and Ko-fi (links in Flat, plain text in VR, which has no browser) and `THIRD_PARTY_NOTICES.md` from the program's folder.
- **Symbols**: `steam-frame/release/upload-symbols.sh <unstripped azahar>` (sentry-cli or `sentry`, `debug-files upload --type elf`); `make-release.sh` runs it when `SENTRY_AUTH_TOKEN` is set, with `SENTRY_ORG` and `SENTRY_PROJECT` from the environment. The token is never written anywhere. The stripped program in the tarball keeps the same build id.
- **Tests**: `src/tests/frame_xr/crash_report.cpp` (classification, the marker, once only, scrubbing, the stack, the keyboard's note, the zip, Send Report to a server on 127.0.0.1). Not in release builds: `AZAHARFRAME_TEST_CRASH_SHOTS=DIR` saves the dialogs of a sample report, `AZAHARFRAME_TEST_CRASH_ANSWER=send|save|dont|keyboard` answers the real dialog after 2 s, `AZAHARFRAME_SENTRY_TEST_CRASH=1` crashes 5 s after start with "Sentry test error <time>", `AZAHARFRAME_TEST_REPORT_PROBLEM=N` opens Report a Problem N s after start (with ANSWER, the note is "Sentry test feedback <time>" and Include a Screenshot is ticked first). `AZAHARFRAME_REPORTS_DIR` moves Save Report's folder.

The `xr: pacing` log line each second has the phase, the game pictures on view for 1 to 6+ refreshes and the cadence, the releases on view for 1/2/3/4+, the holds and the corrections. `AZAHARFRAME_XR_PACE_TRACE=1` logs every frame and latch, for tests |
| `AZAHARFRAME_GPU_BUSY=1` | `video_core/renderer_vulkan/vk_gpu_busy.cpp` | timestamps round the renderer's command buffers (off by default: no query pool, no timestamps). With it, the XR thread's per-second line ends with `GPU busy X ms a refresh (emulator Y in N command buffers, XR pass Z in M draws; P % of T ms)`: the GPU's real working time a refresh, the game's and the controller or projection pass's, against the refresh period (SteamVR's own work is not in it). "GPU behind" is latency, not load |
| `AZAHARFRAME_XR_NO_GPU_WAIT=1` | `vk_xr_target.cpp` | releases images before the GPU is done. A negative test, never for playing |
| `AZAHARFRAME_XR_WATCHDOG=1` | `frame_xr/watchdog.cpp` | logs a frame loop phase that lasts over 50 ms, with the kernel state, wait channel and system call of the frame loop's thread and of the emulator's busy threads. For finding display stalls |
| `AZAHARFRAME_DEBUG_STALL=<where>:<ms>[:<s>]` | `common/debug_stall.h` | sleeps `ms` every `s` seconds (default 5) at `tick` (emu thread after a frame, no lock), `submit` (inside the queue lock), `acquire` (XR frame drawn, not yet handed off) or `release` (the handoff thread, before a release). A test, never for playing |
| `AZAHARFRAME_VMA_BLOCK_MIB` | `vk_instance.cpp` | the size of VMA's memory blocks in MiB (default 32 on the XR device; `0`: VMA's own, 256), to compare |

## Frametanium

[Frametanium](https://github.com/Cogential/frametanium) installs a port from a GitHub release. For an "installer" entry it downloads the asset whose name matches, unpacks it into `~/.local/share/frametanium/apps/<id>`, and runs the `install.sh` at the top of the archive from that folder with no input and a 15 minute limit. On an update the old folder is kept as `.previous`, the new one is unpacked beside it, and `install.sh` runs again; if it fails the old folder comes back. On removal it runs `uninstall.sh` from the same folder, then deletes the folder. It refuses to update or remove while the program in that folder runs, and `install.sh` and `uninstall.sh` also refuse while `azahar` runs.

The tarball fits that: the files are at its top level, the name has `linux-arm64` and ends in `.tar.gz`, `SHA256SUMS` is not mistaken for a download, `install.sh` recognizes an unpacked release by `azahar` and `azaharframe.sh` next to it and installs it in place of a tarball, `uninstall.sh` finds `azahar` next to itself, and the data folder is outside everything Frametanium replaces. Frametanium's `--purge` is not reachable; its remove keeps `~/.local/share/AzaharFrame`. The program folder is kept twice on disk (the unpacked release in Frametanium's folder, and the installed copy), plus `.previous`.

What the owner adds so that Frametanium offers it:

1. **On the Frame**, `~/.config/frametanium/catalog.json` takes one more entry, after the other ports:

   ```json
   {"id": "azaharframe", "name": "Azahar for Frame (3DS VR)", "repo": "simplysanatori/AzaharFrame",
    "asset": "azaharframe-*-linux-arm64.tar.gz", "auto_asset": true, "mode": "installer",
    "prereleases": false, "gameid": "AzaharFrame",
    "description": "My port: Nintendo 3DS games in VR, Azahar with CitraVR's VR mode, native on the Frame."}
   ```

   or, from the Frametanium page or headset app, add `simplysanatori/AzaharFrame` with mode "installer". The release must be published, not a draft. Until the repository is public Frametanium needs a GitHub token (read access to releases is enough) in its `config.json`, `github_token`.
2. **Upstream**, `suggestions.json` in Cogential/frametanium takes `{"repo": "simplysanatori/AzaharFrame", "name": "Azahar for Frame (Nintendo 3DS VR)", "note": "Azahar with CitraVR's VR mode, native; needs your own 3DS games"}`, as in the open pull request for the other ports.
3. **The release** carries `azaharframe-<version>-linux-arm64.tar.gz` (and may carry `SHA256SUMS`). The FrameDrop zip ends in `.zip`, so the asset pattern in the entry does not match it.

After the first install through Frametanium the library entry is the same one `install.sh` makes by hand ("Azahar for Frame"), so installing both ways does not add a second entry.

**No shader warm-up script.** GalaxyFrame ships `warm-shaders.sh` because its shaders can be compiled ahead of play. Azahar's disk cache is filled only by drawing a game on the emulator, so there is nothing to run before the first launch.

## FrameDrop

[FrameDrop](https://framedropvr.com) installs from a manifest. `make-release.sh` also writes `azaharframe-<version>-framedrop-linux-arm64.zip` and `azaharframe.framedrop.json` with `release/make-framedrop-zip.py`: the zip holds the tarball's files plus `run.sh` (`steam-frame/framedrop-run.sh`) at the top, and the manifest (`framedrop.install/v1`) gives the zip's release URL for the tag and its sha256. Attach all three to the release. The install link is `https://framedropvr.com/install?manifest=` followed by the URL-encoded `https://github.com/simplysanatori/AzaharFrame/releases/latest/download/azaharframe.framedrop.json`.

FrameDrop adds its own library entry for `run.sh`. On the first start, and whenever the zip's `VERSION` differs from the one it installed last (kept in `~/.local/state/framedrop-azaharframe/installed-version`), `run.sh` runs `install.sh` with `AZAHARFRAME_SKIP_STEAM=1`, so no second entry is made, and logs to `install.log` in the same folder. Then it starts the installed `azaharframe.sh`. It also gives back the executable bits a zip unpack can lose. If the install fails it starts the version installed before. `FRAMEDROP_RUN_DRY=1` installs if needed and prints what it would start.

## Merging upstream Azahar

The Android app (`src/android`, its CI script, Kotlin format scripts, `AndroidNdkModules.cmake` and the Android-only submodules `libadrenotools`, `libyuv` and `openxr-sdk-src`) is removed from this fork because only the Linux Qt app is built. `#ifdef ANDROID` branches in shared C++ are left as upstream has them. The removed paths are listed in `steam-frame/dev/removed-upstream-paths.txt`. To merge upstream, run `steam-frame/dev/merge-upstream.sh <ref>` (for example `azahar/master` or `2127.0-rc3`): it fetches the azahar remote, merges the ref, deletes any of those paths the merge brings back, then commits, or lists the remaining real conflicts and stops.
